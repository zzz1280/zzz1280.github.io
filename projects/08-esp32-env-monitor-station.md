## 三、技术路线（分阶段）

**技术选型**：ESP32 DevKitC（Arduino 框架 / C++）/ DHT11（起步）或 SHT30（进阶）/ SSD1306 OLED（I2C）/ 后端复用 01 的 Flask，新增传感器 API 与图表页。
> 用 Arduino 框架而不是 MicroPython：简历上"嵌入式 C"更有分量，且和后续 10 号循迹小车、11 号机械臂一脉相承。

- **阶段 0｜采购与接线图（1~2 天）**：Agent 给 BOM（约 30~40 元：ESP32 DevKitC、DHT11 模块、OLED、杜邦线、面包板）+ 接线表；我下单并按图接线，拍照给 Agent 检查。
- **阶段 1｜点亮 OLED（1~2 天）**：Arduino IDE / PlatformIO 环境 → 跑通 SSD1306 显示示例 → 显示自定义文字。产出：屏幕亮了。
- **阶段 2｜读传感器（1~2 天）**：DHT11 读取 + 数据有效性判断（NaN 处理）+ OLED 同屏显示。产出：本地温度计。
- **阶段 3｜连网上报（2~3 天）**：WiFi 连接管理 → 构造 JSON → HTTP POST 到后端 → 服务端校验入库（新增接口 + 表）；失败重试与本地缓存队列。产出：后端数据库里能看到设备上报的数据。
- **阶段 4｜图表页（2~3 天）**：后端查询接口（按时间范围）+ Chart.js 曲线页（温湿度双轴、24h 窗口、30 秒自动刷新）。
- **阶段 5｜收尾（2 天）**：架构图、README、实物照片、长期运行 48 小时稳定性记录，主页卡片更新。

## 四、Agent 运行规范（精简版，务必遵守）

1. 角色：物联网全栈工程师兼导师；重点教我"每一层数据长什么样"——寄存器值、JSON 字段、SQL 行、图表点。
2. 节奏：一次一个阶段，阶段结束汇报并等我确认。
3. 诚实红线：曲线页的数据必须来自真实传感器上报，绝不写脚本伪造数据点；稳定性记录必须真实运行。
4. **实物边界**：接线、上电、拍摄由我完成；Agent 给接线表并核对我的接线照片后再允许上电（防短路烧板）。
5. 范围控制：固件用 Arduino C++ + 两个库（DHT、U3SSD1306 图形库）；不用 MQTT / Home Assistant（v2 再说）；后端改动合并进 01 仓库，不另起炉灶。
6. **安全红线**：WiFi 密码与服务器地址走 `config.h`（gitignore）或编译宏，绝不硬编码提交。
7. 代码规范：固件区分 `sensor / display / net` 模块；后端接口有输入校验；关键逻辑中文注释。
8. 文档同步：每阶段更新「进度日志」。
9. 沟通：上电前接线照片必发 Agent 确认；任何冒烟 / 发烫立即断电拍照提问。

## 五、风险与注意

- DHT11 精度差（±2℃ / ±5%RH）且读数偶发 NaN：代码必须处理；追求效果中途可换 SHT30。
- 家用路由给开发板分 IP 不固定：不影响上报即可，v1 不做固定 IP。
- 长期运行内存碎片导致重启：阶段 5 的 48 小时稳定性测试就是为了暴露这个，遇到就让 Agent 分析日志。
